# Skill: meeting-analysis

## Назначение

Анализ всех транскриптов из папки `calls/` за раз.
Результат — один сводный отчёт в `report.md` в корне проекта.

---

## Когда использовать этот skill

Используй когда пользователь просит:
- «проанализируй созвоны»
- «что решили на встречах»
- «найди проблемы в транскриптах»
- «сделай отчёт по звонкам»
- любой анализ файлов из папки `calls/`

---

## Алгоритм выполнения

### Шаг 1 — Найди все файлы

```bash
ls calls/
```

Прочитай каждый `.md` файл из `calls/` в хронологическом порядке (по дате в имени файла). Читай все файлы до начала анализа — нужна полная картина.

### Шаг 2 — Анализ всех транскриптов вместе

Читая файлы, собирай единые списки по всему периоду:

**Ключевые решения** — что было решено окончательно, кем и когда.
Признаки: «договорились», «фиксируем», «окончательно», конкретная дата + ответственный.
Для важных решений (финансовые, влияют на несколько команд) — добавь контекст.
Для локальных — одна строка.

**Задачи с ответственными** — кто, что, к какому сроку.
Если дедлайна нет — отметить явно.
Если задача повторяется на нескольких созвонах без движения — отметить.

**Открытые вопросы** — что обсуждали, но не решили.
Признаки: «обсудим потом», «надо подумать», «на следующей неделе», вопрос без ответа.

**Блокеры** — что мешает работе прямо сейчас.
Признаки: «жду от», «не могу без», «уже две недели», задача заблокирована другой.
Показывай цепочки: `A ждёт B → B ждёт C → C ждёт A`.

### Шаг 3 — Найди паттерны

После прочтения всех файлов выдели повторяющиеся проблемы:
- Один и тот же блокер на нескольких созвонах
- Решение, которое переигрывали или игнорировали
- Задача без владельца, переходящая из созвона в созвон
- Человек, который системно задерживает других
- Информация, которая искажается при пересказе

Минимум 3 паттерна если файлов больше 3.
Каждый паттерн — с примерами из конкретных созвонов (дата, суть).
Оцени потери: время, деньги, репутация.

### Шаг 4 — Запиши отчёт

Сохрани в `report.md` в корне проекта.
Если файл уже существует — предупреди пользователя и спроси подтверждение перед перезаписью.

---

## Структура report.md

```markdown
# Отчёт по созвонам

**Период:** [дата первого] — [дата последнего]
**Файлов проанализировано:** [N]
**Участники:** [все уникальные участники через запятую]

---

## Ключевые решения

- **[Что решено]** — [Кто] — [Дата созвона]
  [Контекст если важно, иначе пропустить]

---

## Сводная таблица задач

| Кто | Задача | Дедлайн | Созвон |
|-----|--------|---------|--------|
| Имя | Задача | Дата / не указан | дата |

---

## Открытые вопросы

- **[Вопрос]** — поднял [Кто], [Дата]
  Почему завис: [одна строка]

---

## Блокеры

- **[Блокер]** — висит с [Дата], затронуты: [кто]
  Цепочка: [A ждёт B → B ждёт C]

---

## Повторяющиеся паттерны

### Паттерн 1: [Название]
**Что происходит:** [описание]
**Примеры:** [дата] — [что случилось]; [дата] — [что случилось]
**Потери:** [время / деньги / репутация]

### Паттерн 2: [Название]
...

---

## Главные риски

1. **[Риск]** — [Почему критично] — [Что нужно сделать]
2. ...
```

---

## Правила качества

**Баланс деталей:**
- Решение с финансовыми последствиями или влияющее на несколько команд → расписать с контекстом
- Локальная задача с чётким дедлайном → одна строка в таблице
- Технические детали созвонов (фонит микрофон, кто опоздал) → пропускать

**Атрибуция:**
- Всегда указывай кто поднял проблему или принял решение
- Если несколько человек — перечисли всех
- Если неясно — пиши «не зафиксировано»

**Блокеры:**
- Показывай цепочки зависимостей
- Указывай сколько дней/созвонов проблема уже висит

**Паттерны:**
- Только реальные, подтверждённые примерами из текста
- Не додумывай — только то что есть в транскриптах
